# 車輛歷史資料庫 Skill

本 Skill 由六位領域專家使用。專家仍只分析自己的領域；不得把資料庫查詢交回總監代做。

## 查詢方式

每位被呼叫的專家在形成結論前，呼叫一次 `vehicle_history_search`，傳入：

- 自己的 `expert_domain`。
- 本次相關 DTC；沒有則傳空字串。
- 2 至 5 個最能描述本案的繁體中文關鍵詞，例如症狀、零件或發生條件。
- 本次里程；未取得時傳 `0`。
- 每區結果上限 `5`。

不得傳完整 OBD samples、完整 RAG 原文或其他無關內容。工具失敗時清楚標示資料庫證據未取得，不得自行補造歷史紀錄。

## 證據使用規則

- `fixed_vehicle_service_history`：固定車輛的保養與維修履歷，可用於確認零件更換時間、上次保養里程及已做過的檢查。
- `fixed_vehicle_repair_cases`：固定車輛過去故障案例；只有 `data_origin=actual` 且紀錄完整時，才能當成真實歷史事實。
- `same_model_repair_cases`：同型車案例，只能提高或降低檢查優先度，不能直接確認本車故障。
- `maintenance_due`：固定里程套餐提醒，不是故障結論，也不能取代原廠手冊與實車檢查。
- `data_origin=simulated` 的所有資料只供系統展示與流程測試，報告中必須稱為「模擬歷史／模擬案例」。

資料庫、OBD、RAG 與目前量測互相衝突時，以本次實際量測與可重現檢查為優先，並列出衝突與驗證方法。歷史曾更換某零件只能降低優先度，不能排除再次故障；歷史未出現某故障也不能排除本次發生。

## 回覆總監

專家回答中加入簡短的「歷史資料庫比對」：列出命中的固定車輛紀錄、同型車案例、保養到期資訊，以及這些資料如何改變檢查順序。不得貼出完整資料庫回傳內容。
